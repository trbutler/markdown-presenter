# Hub 1214 native MIDI

The audience deck posts this bridge message instead of requesting Web MIDI:

```javascript
{type: 'midi', index: 3, out: 'Lighting', messages: [
    {bytes: [0x90, 60, 100], delayMs: 0},
    {bytes: [0x80, 60, 0], delayMs: 200}
]}
```

PresenterCore validates the complete envelope before it can be sent. `type`, `index`, `out` and `messages` are required and extra keys are rejected. Index must be a finite, exactly representable nonnegative integer; out is a string (empty means the first destination). A batch contains at most 16 messages; an empty batch is a no-op. Each message has exactly bytes and delayMs, with 1-3 integer bytes in 0-255, the first at least 0x80, and a finite numeric delay in 0-10000 milliseconds. Numeric strings, booleans, null, nonfinite values, fractional bytes and out-of-range values are rejected. Fractional milliseconds are accepted. A single malformed message rejects the entire batch. This is the requested short-message transport validation; it does not add SysEx or running-status support or infer status-specific message lengths.

The relay ignores MIDI from subframes or native roles other than audience. DeckController also checks the native role through BridgeMessage.midiRequest(from:). Payloads do not select or impersonate a role. MIDI messages yield no DeckCommands and cause no state broadcast or apply feedback loop. The template remains responsible for once-per-slide emission and directive/channel semantics; Swift sends the validated bytes unchanged.

MIDIOutput creates one MIDIClient and one MIDIOutputPort lazily on a private serial DispatchQueue. Client/port setup, name lookup, scheduling, send and disposal all run off the main thread. It chooses the first MIDIGetDestination whose kMIDIPropertyDisplayName contains out case-insensitively; an empty out chooses the first destination. Results, including no match, are cached by case-folded output selector. A setup-changed notification invalidates the cache so the next batch re-resolves it. A missing selector is logged once while absent, and the complete batch is dropped; an observed successful resolution permits a later missing-device warning again.

All message delays share one DispatchTime origin per batch. Zero-delay bytes are sent immediately on the worker; delayed bytes use asyncAfter. Each send uses one MIDIPacketList with timestamp zero and inline storage sufficient for three bytes. MIDISend copies the bytes before the local buffers leave scope. Delayed note-offs stay bound to the endpoint selected with the original batch, even if another batch chooses a different output or setup changes. If that endpoint disappears, MIDISend can fail; this is logged with repeated identical endpoint errors suppressed. Notes are not deliberately cancelled merely because the next slide is selected.

Shutdown stops new scheduled sends, immediately flushes every pending note-off to its original endpoint, and then sends All Notes Off (CC 123, value 0) once per endpoint/channel used. This includes channels with successful channel-voice sends and channels whose pending offs are flushed. Both explicit note-offs (0x8n) and velocity-zero note-ons (0x9n) are tracked, with independent tokens for repeated notes. A scheduled off is removed only after a successful send; a failed off remains available for the shutdown retry. Non-note delayed messages are dropped at shutdown. Normal slide changes do not cancel pending offs.

The MIDI worker completes the flush before disposing the port and then the client. AppDelegate returns terminateLater and replies when that work completes, or at a 500 ms deadline, whichever arrives first. Waiting is asynchronous; the main actor remains free to run. The deadline bounds how long normal termination waits even if a CoreMIDI call stalls. After that deadline, force termination, device removal or a driver failure can still prevent delivery. CC 123 can affect other notes on those same endpoint/channels; it is intentionally sent on shutdown as the requested fallback, including when a note-on had no explicit scheduled off. No other MIDI controllers are reset.

The browser's notes/service status remains the existing fail-soft status: in the app it says MIDI is sent by the app. Native missing-port and send errors are logged, without stopping the presentation. This patch does not change the JavaScript status contract, README, template or design document outside macos/; their Swift-TODO statements are superseded by this implementation.

## Validation still required on a Mac

No Swift toolchain is available here. The parser tests were added but neither built nor run, and no real MIDI client/device was opened. VERIFY-ON-MAC comments mark CoreMIDI notification block signatures and enum import, CFString ownership/import, MIDIPacketList pointer/size signatures, and AppKit's terminateLater/reply lifecycle. Compile on Swift 5.9/macOS 13 with strict concurrency checking, then separately validate enumeration/hot-plug, display-name matching, program/control messages and delayed note-offs with the intended MIDI destination. Check quitting within 200 ms of a note-on, shutdown CC 123 on each used channel, and the 500 ms deadline if the worker stalls. DispatchQueue delay scheduling is not a real-time timing guarantee.
